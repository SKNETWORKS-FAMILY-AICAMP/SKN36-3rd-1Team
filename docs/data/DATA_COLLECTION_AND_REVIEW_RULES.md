## 1. 목적 및 핵심 철학

본 규정은 복지로(Bokjiro), 정부24, 온통청년, 공공기관 및 지자체 포털의 복지·지원 정책 데이터를 수집하고 정제하는 과정에서 발생하는 **환각(Hallucination), 허위 주소(404), 포털 첫 화면 오인, 자의적 기준 추정, 인용문 불일치, 조건 위계 왜곡, 접수 상태 혼동, 장부 사후 조작 등의 문제를 원천 차단**하기 위해 제정되었다.

### 5대 기본 철학
1. **Zero Hallucination (추정·조작 절대 금지)**: 공식 원문에 명시되지 않은 정책명, 자격 요건, 금액, 신청 주체, 날짜, URL은 절대 지어내지 않는다. 모르면 `확인 불가` 또는 `날짜 없음`으로 둔다.
2. **100% Byte-level Verification (원문 바이트 대조)**: 인용된 모든 근거 문장은 로컬에 다운로드된 원본 문서(HWP, PDF, HTML) 내에 실제 존재함을 자동화 코드로 검증한다.
3. **Traceable Manifest & Immutable History (장부 불변성 및 출처 추적)**: 모든 수집 파일과 근거 URL은 수집 당시 실행 스크립트와 호출 시각이 기록된 장부(`_manifest.tsv`)로 1:1 증명되어야 하며, 사후 추정값이나 재계산 결과를 원본 수집 기록으로 위장하지 않는다.
4. **Structured Conditions & Logic Preservation (조건 위계 및 논리 보존)**: 기본 필수조건과 우대·특례·연계서비스 조건을 혼합하지 않고, 수치가 포함된 조건(근로시간·기간, 차량 규격 등)을 단순 자격 상태로 왜곡하지 않는다.
5. **Decoupled Application URL & Intake Status (신청 경로와 접수 상태 분리)**: 신청 URL의 물리적 성격(전용 신청화면/정책안내/기관 첫화면)과 실제 사업의 모집 접수 상태(접수중/접수종료/상시)를 독립된 정보로 엄격히 분리한다.

## 2. URL 수집 및 주소 장부(_manifest.tsv) 관리 규정

### 2.1 주소 장부(Manifest) 작성 의무
- 수집된 모든 원본 파일(PDF, HWP, HWPX, HTML 등)은 수집 즉시 주소 장부(`data/.../_manifest.tsv`)에 등록되어야 한다.
- **장부 필수 열**:
  | 열 이름 | 설명 | 예시 |
  |---|---|---|
  | `저장 파일` | 로컬에 저장된 실제 파일명 | `POL_010_work24_intro.html` |
  | `받은 주소` | 파일을 실제로 내려받은 완전한 URL (리다이렉트 시 최종 URL) | `https://www.work24.go.kr/...` |
  | `받은 시각` | 수집 실행 시각 (ISO 8601 또는 `YYYY-MM-DD HH:MM:SS`) | `2026-11-17 10:15:20` |
  | `받은 스크립트`| 수집을 수행한 스크립트 파일명 | `scripts/collect_issue18_apply22.py` |

### 2.2 근거 URL 기재 원칙
1. **장부 외 URL 기재 금지**: 보고서나 DB의 `근거 URL` 칸에는 **반드시 `_manifest.tsv`에 등록된 주소만** 기재한다.
2. **첨부파일 다운로드 주소 우선**: 근거 문장이 첨부 지침(PDF/HWP)에 있는 경우, 상세 안내 화면 URL이 아닌 해당 지침 파일의 실제 다운로드 주소를 근거 URL로 기재한다.
3. **다운로드 실패 시 동일 지침 매핑**: 파일 다운로드 오류 발생 시, 동일 지침을 공유하는 다른 정책 파일의 장부 등록 URL을 근거로 사용하고 비고에 사유를 명시한다.

### 2.3 포털 대표(루트) 주소 단독 기재 엄금
- `https://www.work24.go.kr`, `https://korea-pass.kr/`, `http://www.kics.go.kr` 등 **포털 대표 첫 화면 URL을 정책 전용 안내나 신청 URL에 단독 기재하는 것을 엄격히 금지**한다.
- **처리 기준**:
  - 해당 정책의 전용 온라인 접수 화면이 확인된 경우에만 `신청 화면`으로 기재한다.
  - 전용 신청 화면이 없고 포털 첫 화면만 확인되는 경우: **제안 주소 칸을 비우고(`""`), 비고 칸에 `첫 화면만 확인: https://...`** 형태로 기록하며 조치 제안을 `비움`으로 판정한다.
  - 첫 화면에서 정책 소개 페이지(예: `.../info/intro.do`)가 별도로 존재하는 경우 해당 정책 안내 페이지를 제안 주소로 사용한다.

### 2.4 URL 임의 추정 및 404 주소 방지
- URL의 파라미터(일련번호, 메뉴 번호 등)를 임의로 변경하거나 추측하여 작성하지 않는다.
- 모든 URL은 HTTP 200 응답 및 실제 정책 내용 표출 여부를 확인한 최종 URL만 사용한다.

### 2.5 [신설 v1.1] 수집 장부 감사 및 사후 위조 방지 규정
1. **사후 추정값의 원본 위장 금지**: 사후에 다시 계산한 SHA256 해시, HTTP 재요청 결과, 사후 재구성한 manifest를 과거 수집 시점의 원본 기록인 것처럼 기술해서는 안 된다.
2. **수집 시점과 감사 시점의 엄격한 분리**: 검증 시에는 다음 4가지 메타데이터를 반드시 분리하여 기록한다.
   - `최초 수집 시점 기록값` (원본 manifest의 주소·시각)
   - `현재 저장 파일 검증값` (현재 파일 존재 여부, 현재 계산된 SHA256)
   - `스크립트 분석 결과` (수집 직후 실시간 기록인지, 일괄 후처리 생성인지)
   - `실행 로그 검증값` (과거 실행 로그에 보존된 실제 HTTP 상태코드, 리다이렉트 체인)
3. **로그 부재 시 확정 금지**: 과거 실행 로그가 존재하지 않아 수집 시점의 실제 HTTP 상태나 응답을 확인할 수 없는 경우, 현재 재요청 결과로 과거 상태를 소급 단정하지 말고 **`확인 못 함` 또는 `로그 없음`**으로 기록한다.
4. **HTTP 200 맹신 금지**: HTTP 200 응답이라 하더라도 자바스크립트 오류 화면, 세션 만료 안내, 접속 차단(403 변형), 또는 대표 포털로 자동 리다이렉트된 경우가 있으므로, 반드시 본문 텍스트가 정상적인 정책 내용을 담고 있는지 바이트 수준에서 검증해야 한다.
5. **원본 Manifest 불변성**: 기존 `_manifest.tsv`는 절대 덮어쓰거나 수정하지 않으며, 감사·검증 결과는 별도의 `_manifest_audit.md` 및 `_manifest_verification.tsv`로 분리 작성한다.

## 3. 최신성 및 지침 기준 연도 검증 규칙 (규칙 5)

### 3.1 2026년 최신성 원칙 (규칙 5)
- 조사 기준 연도(2026년) 대비 **2026년도 최신 지침·원문이 부재하고 2025년 이하 지침만 확인되는 경우, 핵심 자격 요건 판정을 반드시 `확인 불가`로 확정**한다.
- 과거 지침에 기재된 숫자는 `과거 기준 참고값`으로만 취급하며, 2026년 현행 확정값으로 처리하지 않는다.

### 3.2 기준 연도 표기 규칙
- 원문에 명시된 공식 날짜(표지 발간일, 개정일, 시행일, 공식 공고일)만 기록한다.
  - 형식: `YYYY년 (YYYY.MM.DD)` 또는 `YYYY년`
- 원문에 명시적인 날짜가 없는 경우 반드시 **`날짜 없음`**으로 표기한다. 크롤러 실행일을 지침 기준으로 둔갑시키지 않는다.

## 4. 근거 문장 추출 및 100% 바이트 단위 대조 규칙

### 4.1 로컬 파일 100% 바이트 일치 검증
- 보고서에 기재되는 모든 `근거 문장(원문 그대로)`은 로컬 저장 파일의 원문 텍스트와 100% 부분 문자열로 일치해야 한다.
- 일치 유형은 `EXACT_MATCH`(완전 일치), `NORMALIZED_MATCH`(공백·줄바꿈 정규화 일치), `NOT_FOUND`(추출 성공했으나 미발견), `EXTRACTION_FAILED`(추출 실패), `SOURCE_MISSING`(파일 없음)으로 분류한다.

### 4.2 판정을 직접 뒷받침하는 핵심 문장 선정
- 서식 명칭, 목차, 관계 법령 조항 명칭만 단독으로 떼어내 근거 문장으로 사용하는 것을 금지한다.
- 판정 대상(연령 수치, 소득 기준, 접수 기관)이 직접 서술된 문장만을 인용한다.

### 4.3 [신설 v1.1] 의미 충족성 독립 검증
- 바이트 일치(`EXACT_MATCH`)하더라도 다음 항목을 독립적으로 2차 검증해야 한다:
  1. 인용문이 해당 정책(policy_id)의 조건이 맞는가?
  2. 적용 대상(신청자 본인 vs 자녀 vs 부모)이 일치하는가?
  3. 기본 필수조건인지, 우대·선택 조건인지 왜곡되지 않았는가?
  4. 근거 문장이 해당 수치와 판정을 온전히 입증하는가?
- 바이트 일치와 의미 충족성은 별도 필드로 관리하며, 자동화 코드 확정이 어려우면 `수동 검토 필요`로 표시한다.

### 4.4 [신설 v1.1] FAQ 및 동적 콘텐츠 수집 검증 규정
1. **정적 HTML 본문 부재와 실제 질문 0건의 엄격한 분리**:
   - 수집된 정적 HTML 파일 내에 질문 텍스트가 존재하지 않는 경우, 이를 **`실제 FAQ 0건`으로 왜곡 해석하지 말고 `수집 질문 0건(동적 로드 확인 필요)` 또는 `검증 불가`**로 기록한다.
   - SPA(Vue, React), iframe, 비동기 AJAX 호출로 FAQ가 로드되는 사이트의 경우 동적 렌더링 한계를 명시한다.
2. **물리적 DOM 단위 대조**:
   - 추출된 FAQ 질문 수는 단순 줄바꿈이나 문자열 개수가 아닌, 공식 페이지의 실제 질문 아코디언/항목(DOM Node) 개수와 대조되어야 한다.
   - 이미지 카드뉴스(예: 3장)를 3개의 FAQ 텍스트 질문으로 둔갑시키지 않는다.
3. **관련 없는 상품·제도 FAQ 혼동 금지**:
   - 기관 자체의 일반 보증 상품 FAQ(예: HUG 전세보증금반환보증 금융상품 FAQ)와 정부·지자체의 지원사업 FAQ(예: 청년 전세보증금반환보증 보증료 지원사업 FAQ)를 명확히 구분한다. 지원 대상 사업과 무관한 FAQ를 해당 정책의 FAQ로 기재하지 않는다.

## 5. 조건 구조화 및 신청 경로 표준화 규칙

### 5.1 복수 수치 기준의 독립 행 분할 (Row Split)
- 하나의 정책에 대상자군별로 다른 연령/소득 수치 기준이 적용되는 경우(예: 청년 5천만원, 일반 6천만원, 신혼부부 7.5천만원), 절대로 단일 행에 묶지 않고 **기준 수치마다 별도의 행으로 분할**한다.

### 5.2 정량 데이터와 자격 상태의 엄격한 분리
- **숫자 칸**: 순수 숫자(또는 범위)만 입력한다. 비교 연산자를 포함하지 않는다.
- **수치가 포함된 조건의 자격상태 오분류 금지**:
  - `주 30시간 이하`, `근로기간 3개월 이하` 등은 단순 자격 상태가 아니라 **근로시간·근로기간에 대한 수치 조건**이므로 독립된 수치 조건으로 구조화한다.
  - `12인승 이하`, `1년 이상 리스·렌트`, `세대당 1대` 등 차량 제원 조건 역시 각각의 수치 조건으로 독립 행 분할한다.

### 5.3 [신설 v1.1] 조건의 성격 및 결합 논리 구조화 규정 (표 C 표준)
조건 표는 단일 표를 유지하되 다음 열을 필수 포함하여 위계와 논리를 보존한다:
1. **조건 성격**:
   - `기본 필수`: 해당 정책의 기본 수혜를 받기 위해 모든 신청자가 충족해야 하는 필수 조건 (예: K-패스 기본 가입, 청년수당 기본 요건)
   - `우대·특례`: 기본 대상자 중 추가 혜택·환급률을 받기 위한 선택적 요건 (예: K-패스 청년·저소득·다자녀 우대, 우대조건 미충족 시에도 기본 서비스 이용 가능)
   - `연계서비스`: 통합 신청 시 부가적으로 제공되는 외부 연계서비스의 전제조건 (예: 행복출산 내 다자녀 KTX·SRT 할인)
   - `소급지원`: 기본 자격 외에 과거 기간 소급 적용 기한 (예: 행복출산 출생 후 60일 소급 기한)
   - `제외`: 명시적인 참여 배제 요건 (예: 중복 사업 참여자 제외)
   - `신청절차`: 자격 요건이 아닌 행정적 제출·접수 절차에 관한 요건
2. **조건 그룹 ID 및 결합 관계**:
   - `조건 그룹 ID`: 동일한 적용 단위로 묶이는 그룹 식별자 (예: `GRP_BASE`, `GRP_YOUTH_PREF`, `GRP_INCOME_PREF`)
   - `그룹 내 결합 관계`: 그룹 내부 조건 간 결합 논리 (`AND`, `OR`, `단일`)
   - `그룹 간 결합 관계`: 그룹 간의 논리적 결합 (`필수 AND`, `선택 OR`, `선택 옵션`)
3. **적용 대상 및 수치 메타데이터**:
   - `적용 대상`: `신청자 본인(applicant)`, `자녀(child)`, `가구(household)`, `차량(vehicle)` 등
   - `비교 연산자`: `<=`, `>=`, `<`, `>`, `==`, `BETWEEN` 등
   - `단위`: `세`, `시간/주`, `개월`, `원/년`, `%` 등

### 5.4 [신설 v1.1] 신청 URL 역할 및 접수 상태 분리 규정 (표 E 표준)
신청 경로 조사 표는 다음 3대 정보를 독립된 열로 작성하여 통계적·논리적 혼동을 배제한다:
1. **URL 역할·성격**:
   - `신청 화면`: 실제 해당 정책의 온라인 신청·접수가 이루어지는 전용 화면
   - `정책 안내 화면`: 해당 정책의 상세 소개, 모집 공고, 지원 내용이 표출되는 화면
   - `기관 첫 화면`: 소관 기관 또는 포털의 최상위 메인 페이지 (전용 안내 부재)
   - `접속 불가`: 403, 404, 도메인 만료, 무한 리다이렉트 등으로 연결되지 않는 주소
   - `확인 불가`: 기술적 또는 권한 문제로 화면 성격을 확정할 수 없는 주소
2. **조치 제안**:
   - `변경`: 신규 검증된 유효 안내·신청 주소로 교체 제안
   - `유지`: 현재 등록된 주소가 최선의 유효 정책 안내/신청 화면임
   - `비움`: 전용 안내/신청 주소가 없고 첫 화면만 확인되거나 지자체별 상이하여 주소란 공란(`""`) 제안
   - `제외`: 사전 협의에 따라 조사 대상에서 제외된 정책
3. **현재 접수 상태**:
   - `접수 중`: 검증일 기준 실제 모집·신청이 진행 중임이 공고문으로 확인됨
   - `접수 예정`: 향후 모집 개시일이 명시되어 있음
   - `접수 종료`: 공고된 모집 기간이 경과하여 현재 접수가 마감됨
   - `상시 접수`: 연중 상시 또는 예산 소진 시까지 상시 접수함
   - `확인 불가`: 모집 일정이나 현행 접수 여부를 확인할 수 없음
   - `해당 없음`: 직권 선발, 조사 제외 등 접수 상태 판정이 불필요한 경우
4. **접수 상태 판단 원칙**:
   - 과거 연도(예: 2023년, 2024년) 공고가 존재한다는 이유만으로 현재 접수 중으로 단정하지 않는다.
   - 모집 기간이 명시되지 않은 단순 소개 화면인 경우 `확인 불가` 또는 `상시 접수(근거 확인 시)`로 기록한다.

## 8. 독립 검증 엔진 및 검증 결과 JSON 표준 (v1.2 추가)

> 이 절은 이슈 #18에서 발견된 **원문 검증 실패를 `100% / PASS`로 잘못 집계한 문제**의 재발을 방지한다. 앞선 출처·최신성·인용문·조건 구조·접수 상태 규칙을 대체하지 않고 **추가로 적용**한다. 적용 범위는 이슈 #18뿐 아니라 이후 모든 정책 수집·검수 작업이다.

### 8.1 검증 엔진과 보고서 생성기 분리

1. **독립 검증 엔진**은 실제 제출된 보고서 표, 각 행이 참조하는 원본 파일, 대상 정책 목록 및 원본 `_manifest.tsv`를 직접 읽는다. 보고서 생성 코드 안의 별도 예상 행 목록을 검증 대상으로 대체하지 않는다.
2. **보고서 생성기**는 검증 엔진이 저장한 JSON 결과만으로 검증 통계와 판정을 계산한다. 검증 이전의 예상 건수, 성공률 `100%`, `PASS` 등의 고정 문자열을 사용하지 않는다.
3. 검증 실패, 입력 누락, 문서 파싱 실패, 검증 범위 미충족, 결과 JSON 스키마 오류 시에는 **실패 시 안전하게 종료(fail closed)**한다. 검증 결과가 없는데 완료 보고서를 생성하지 않는다.
4. Markdown 보고서의 정책별 행 수는 **실제 표 본문에서 계산**한다. 제외 정책은 검증 대상 범위에 포함하되 `EXCLUDED`로 별도 집계하며, 통과 건수에 포함하지 않는다.
5. 자동 원문·정합성 검증과 사람이 수행하는 **의미 검증/정책 동일성 최종 승인**을 구분한다. 단순 문자열 일치로 전체 품질 승인을 대체할 수 없다.

### 8.2 JSON 결과 계약과 상태 코드

- JSON은 UTF-8 인코딩의 유효한 문서여야 하며, `schema_version`을 명시한다.
- 실행 메타데이터: `run_id`, `verified_at`(타임존 포함 ISO 8601), `verifier.name`, `verifier.version`, `verifier.code_sha256`.
- 입력 메타데이터: 보고서·대상 JSON·manifest의 **상대경로**, 실행 당시 SHA256 및 사용 여부를 저장한다. 절대 로컬 경로나 API 키, 쿠키, 토큰을 결과에 저장하지 않는다.
- 검증 범위: 표별 `rows_detected`, `rows_checked`, `rows_excluded`, `rows_unchecked`; 실제 행별 결과에서 집계한다.
- 행별 정보: `record_id`(한 표 안에서 유일한 행 식별자), `table_id`, `policy_id`, `source_file`, `source_url`, `source_file_sha256`, `source_match`, `url_match`, `policy_identity`, `semantic_validation`, `freshness`, `final_status`, `issues`.
- 한 행에서 여러 문제가 발견되면 `issues` 배열에 각각 오류 코드를 기록한다. 단일 주 상태만으로 원인을 은폐하지 않는다.

| 필드 | 허용 값 | 판정 원칙 |
|---|---|---|
| `source_match` | `EXACT_MATCH`, `NORMALIZED_MATCH`, `NOT_FOUND`, `SOURCE_MISSING`, `EXTRACTION_FAILED` | 추출된 텍스트에서 인용문 존재 여부를 검증한다. 원본 바이너리의 해시와 텍스트 문자열 일치는 서로 다른 개념이다. |
| `url_match` | `MATCH`, `MISMATCH`, `UNKNOWN` | 실제 저장 원본의 출처와 manifest 기록을 대조한다. 현재 다시 연 주소는 과거 수집 URL로 간주하지 않는다. |
| `policy_identity` | `VERIFIED`, `MISMATCH`, `REVIEW_REQUIRED` | 정책 ID·정책명·지역·기관·사업 내용의 동일성을 따로 검증한다. |
| `semantic_validation` | `VERIFIED`, `NOT_SUPPORTED`, `REVIEW_REQUIRED` | 인용문이 **그 행의 조건 판정**을 직접 뒷받침하는지 검증한다. 자동 확정이 곤란하면 `REVIEW_REQUIRED`. |
| `freshness` | `CURRENT`, `OUTDATED`, `UNKNOWN` | 원문의 시행·기준연도를 검증한다. 과거 지침 수치는 현행 확정값이 아니다. |
| `final_status` | `PASS`, `FAIL`, `PENDING`, `EXCLUDED` | 아래 게이트를 만족한 경우에만 PASS. |

`NORMALIZED_MATCH`는 공백·줄바꿈 등 **의미를 바꾸지 않는 서식 차이**만 허용한다. 숫자·단위·비교 연산자·부정문을 바꾸지 않는다. 정규화 방법과 원문 텍스트를 함께 보존한다. **완전 바이트 일치라는 표현은 실제 파일 바이트를 대조했을 때만 사용**하고, 추출 텍스트의 일치는 `EXACT_MATCH`로 구분해 기록한다.

### 8.3 행별 판정 및 전체 품질 게이트

1. `PASS`: 원문 추출 및 인용 검증 성공(`EXACT_MATCH` 또는 정당한 `NORMALIZED_MATCH`), URL 정합성 `MATCH`, 정책 동일성 `VERIFIED`, 의미 검증 `VERIFIED`, 필요한 현행성 검증 `CURRENT`를 모두 충족한 경우. 현행성 판단이 적용되지 않는 항목은 별도 근거와 함께 예외로 명시한다.
2. `FAIL`: 원문 미발견, 잘못된 정책 연결, 잘못된 URL 연결, 의미 미충족 등 **확인된 오류**가 있는 경우.
3. `PENDING`: 파일 추출 불가, 확인할 자료 없음, 사람 검토 필요 등 **검증 미완료**인 경우. 확인 불가를 PASS로 합산하지 않는다.
4. `EXCLUDED`: 사전에 승인된 조사 제외 행에만 허용하며, 제외 사유를 기록한다. 단순 검증 실패를 제외로 처리하지 않는다.
5. 실행 전체 `PASS`는 **검증 대상으로 확인한 모든 행이 검증되고**, 제외 사유가 정당하며, `FAIL`과 `PENDING`, 미검사 행이 모두 0이고, 전체 필수 점검 게이트가 통과한 경우에만 허용한다.
6. `rows_detected = PASS + FAIL + PENDING + EXCLUDED + rows_unchecked` 등 모든 집계의 일치를 기계적으로 검사한다. `rows_unchecked > 0`이거나 합계 불일치면 전체 PASS를 차단한다.
7. 실행 오류(스키마 누락, 파일 읽기/파싱 실패)는 `PASS` 대신 `ERROR`로 종료한다. 전체 상태는 `PASS / FAIL / PENDING / ERROR` 중 하나를 사용한다.

### 8.5 변조 테스트(Tamper Test) 및 회귀 테스트

- 검증 테스트는 **원본이 아닌 임시 복사본**에서만 수행한다. 기존 원본 문서·manifest·수집 로그를 변조하지 않는다.
- 필수 **정상 통과 테스트**와 다음 실패 탐지 테스트를 자동화한다.
  1. 저장 파일 삭제 → `SOURCE_MISSING` 및 최종 PASS 차단
  2. 인용문 한 글자 변조 → `NOT_FOUND` 또는 관련 불일치 및 PASS 차단
  3. 다른 `policy_id`로 바꿔 연결 → `POLICY_ID_MISMATCH` 및 PASS 차단
  4. 원본 URL·manifest URL 변경 → `URL_MISMATCH` 및 PASS 차단
  5. 다른 정책의 파일로 연결 → `POLICY_IDENTITY_MISMATCH` 및 PASS 차단
  6. 추출 불가능한 파일 → `EXTRACTION_FAILED` 및 `PENDING/ERROR` 처리
  7. 의미 검증 `REVIEW_REQUIRED` → 최종 `PENDING` 유지
  8. 실제 행 추가·삭제 또는 표 파싱 실패 → 범위 불일치 검출 및 전체 PASS 차단
  9. JSON 집계를 손으로 `100% / PASS`로 조작 → 원자료 재계산과 불일치 검출
- 단순히 모든 테스트 데이터를 `FAIL`로 반환하는 잘못된 검증기를 막기 위해 정상 데이터는 실제 `PASS`가 되어야 한다.
- 테스트 결과에는 실행 시각, 테스트명, 기대 상태, 실제 상태, 결과, 코드 버전을 남긴다. 테스트 통과와 **실제 조사 데이터의 품질 승인**은 별도로 판정한다.

### 8.6 이중 규칙서 반영 및 버전 관리

- 이 절을 `LifePolicy AI/docs/data/DATA_COLLECTION_AND_REVIEW_RULES.md`와 `4차_준비` 아래 해당 원본 규칙서 **두 곳 모두**에 반영한다.

## 9. 기존 검증 자산 재사용과 이슈 #18 신규 검증 경계 (v1.3 추가)

> **목적:** 3차 LifePolicy AI의 클로드 검증·릴리스 자산을 정본 계약으로 재사용하고, 4차 이슈 #18의 원문·정책 동일성·자격조건 의미·신청 페이지 검증만 보완한다. 기능이 비슷하다는 이유로 검증의 *수행 범위*까지 동일하다고 간주하지 않는다. 이 장은 1~8장을 대체하지 않는다.

### 9.1 역할과 기준선(SSOT)

1. **정책 식별 및 데이터 계약 기준:** `LifePolicy AI/data/handoff/data_contract.md`와 후보 릴리스의 실제 정책 레코드를 읽고, 정책의 `policy_id`를 임의로 변경하거나 새 체계로 재발급하지 않는다. `data/metadata/id_mapping.csv` 및 `data/metadata/data_corrections_v1.4.0.json`의 기존 매핑·교정 이력을 우선 확인한다.
2. **후보 릴리스 기준:** `data/releases/v1.4.0-candidate/manifest.json`에 기록된 파일·버전·SHA256을 기준으로 후보 데이터를 특정한다. 과거의 검증 로그가 다른 manifest 해시를 가리키면 현 후보 통과 근거로 재사용하지 않는다.
3. **조건 그룹 계약:** 기존 `ConditionGroup`, `EligibilityCondition` 및 `HAS_ROOT_CONDITION_GROUP`, `CONTAINS_GROUP`, `CONTAINS_CONDITION`의 모델과 `data/handoff/data_contract.md` 규격을 준수한다. 조사용 표 C의 그룹을 별도의 영구 정책 ID 또는 신규 DB 스키마로 확정하지 않는다.
4. **신청 URL 근거:** `data/metadata/application_url_evidence_v1.4.0.json`은 기존 공식 출처·추출 근거 목록이다. 실제 접수 화면을 *현재 열어 확인했다는 증거*로 해석하지 않는다.
5. 3차 정본과 4차 조사 파일이 충돌하면 우선 **차이 보고서**를 작성하고, 양쪽 정책명·기관·지역·공식 ID·수집 원문을 비교한다. 단순히 최신 파일에 적혀 있다는 이유로 원본 정책명을 바꾸지 않는다.

### 9.3 신규 검증에 필요한 최소 기능 (이슈 #18 전용)

1. **정책 동일성:** 대상 JSON의 `policy_id` ↔ 기존 후보의 `policy_id` ↔ 보고서의 정책명·기관·지역·공식 ID ↔ 저장 원문을 교차 검증한다. 표기가 다른 경우 동의어/약칭인지, 다른 지원사업인지 증거를 제시한다. `policy_identity`를 고정 `VERIFIED`로 설정할 수 없다.
2. **인용문·출처 정합성:** 보고서 표 C·E의 *실제 행*을 파싱하고 근거 문장, 원본 저장 파일, 수집 당시 manifest의 URL을 대조한다. `NOT_FOUND`, `SOURCE_MISSING`, `URL_MISMATCH`를 숨기지 않는다. 원문 문자열 일치가 정책 의미 충족을 자동으로 보장하지 않는다.
3. **자격 조건 의미 검증:** 기본/우대/소급/연계/제외 구분, 적용 대상(신청자/자녀/가구), 수치·단위, 정책 유형별 AND/OR/NOT의 결합을 테스트한다. 특히 차량 소유 OR 장기 리스·렌트, 대상 유형별 소득 한도, 미취업 OR 단기근로 예외는 경계값·반례를 포함해야 한다. 기존 그래프의 `ConditionGroup` 구조와 일치하도록 **매핑 제안**만 작성한다.
4. **신청 URL 검증:** 주소의 역할(정책 안내/실제 신청/기관 첫 화면/접속 불가)과 현재 접수 상태를 구분한다. 과거 모집 공고, 지역 불일치, 리다이렉트, 공식 URL 접근 제한을 구분한다. `official_apply_url`을 실제 DB에 적용하지 않는다.
5. **검증 불가와 차단:** 공식 자료·브라우저 접근·현행 기준이 확인되지 않은 경우 `PENDING`으로 남기며 핵심 자격조건의 단정적 추천 판정을 금지한다. 정책 연결 오류처럼 확인된 오류는 `FAIL`로 구분한다.

### 9.4 검증 결과 통합 계약

- 8장의 JSON 표준(`schema_version`, `run_id`, `verified_at`, `verifier`, `inputs`, `coverage`, `results`, `summary`, `overall_status`)을 **공통 출력 계약**으로 사용하고 새 상태 체계를 임의로 만들지 않는다.
- 결과 각 행에 `validation_layer` (`STRUCTURE`, `PACKAGE`, `SOURCE_QUOTE`, `POLICY_IDENTITY`, `CONDITION_SEMANTIC`, `APPLICATION_URL` 등) 및 `validator_source`(기존 스크립트명 또는 이슈 #18 검증기)를 함께 기록할 수 있다. 각 층의 PASS는 해당 범위의 성공일 뿐 전체 데이터 활용 승인과 다르다.
- 기존 검사 결과를 통합할 때는 `source_manifest_sha256`, `input_sha256`, `execution_type`(`ACTUAL_RUN`, `HISTORICAL_REPORT`, `CODE_REVIEW_ONLY`)을 구분한다. 실행하지 않은 코드를 실행 완료로 보고하거나 과거 성공을 현재 후보 성공으로 기록하지 않는다.
- 집계는 JSON의 행별 상태에서 계산하고 기존 검사 결과와 중복 집계하지 않는다. 검증 코드가 예상 행 수나 전체 PASS를 하드코딩할 수 없다.
- `policy_identity=MISMATCH`, 원문 미발견, 조건 논리의 확인된 오류 등은 전체 `FAIL`로 반영한다. 미검증 항목은 `PENDING`으로 남긴다. 정상 사례와 변조 사례를 모두 검증하는 8.5의 통합 테스트를 수행한다.
