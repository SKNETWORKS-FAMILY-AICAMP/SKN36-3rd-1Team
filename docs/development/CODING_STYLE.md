> 버전: 1.0 (팀 검토용)  
> 적용 프로젝트: 생애주기 맞춤형 정부·지자체 정책 추천 및 근거 기반 질의응답 서비스  
> 참고 원본: `CODING_STYLE.md` (LabBridge 팀 공통 스타일; 핵심 원칙 계승)  
> 기획 기준: [PRD](../product/PRD.md), [Notion WBS](https://app.notion.com/p/1c9896a6387283e0924f81be54a9b726)
> 적용: 데이터 수집·전처리, Graph/Vector DB, Python/FastAPI, RAG/LLM, 웹 UI, 테스트·문서  
> 상태: **초안** — 팀 합의가 필요한 항목은 아래 '결정 대기'에 명시

## 1. 한 문장 원칙

**짧은 코드보다 흐름이 보이는 코드, 복잡한 설계보다 지금 필요한 구조, AI가 만든 코드라도 담당자가 설명하고 검증할 수 있는 코드.**

이 기준은 팀원들의 경험 차이를 줄이기 위한 공통 약속이다. 이해하기 쉬운 구현을 우선하되, **정책 데이터의 출처·기준일·무결성**과 **사용자 정보 보호**를 단순화를 이유로 희생하지 않는다.

## 2. 규칙 우선순위와 작업 범위

규칙이 충돌하면 다음 순서로 판단한다.

1. 개인정보 보호·비밀키 관리·데이터 무결성·기본 보안
2. 확정된 PRD, 팀의 API/데이터 계약 및 WBS 일정
3. 이미 합의한 코드·폴더 구조 및 공통 인터페이스
4. 이 문서의 일관성·단순성·가독성
5. 개인 취향

3차 MVP 개발 완료 목표는 **11월 8일**이다. MVP는 공식 정책 원문 수집·정제부터 Graph DB·Vector DB 조회, 사용자 조건 확인, LLM 답변·공식 출처 출력까지 포함한다. 계정 장기 관리, 정기 알림, 브라우저 신청 대행, MCP/Multi-Agent/Fine-tuning은 팀에서 별도 확정하지 않으면 선구현하지 않는다.

## 3. 모든 언어 공통 원칙

- 입력 → 검증 → 처리 → 결과/오류의 흐름을 위에서 아래로 이해할 수 있게 작성한다.
- 함수·파일은 하나의 책임에 집중한다. 외부 API, DB, 데이터 변환, UI는 실패 양상이 달라 필요하면 분리한다.
- 의미 있는 변수·함수명을 사용한다. 짧은 한 줄보다 읽기 쉬운 여러 줄을 택한다.
- 주석은 **왜 그렇게 했는지**, 정책 원문의 예외 조건이나 선택한 기술적 이유를 기록한다.
- 반복·테스트·변경 경계가 생길 때 분리한다. 아직 필요 없는 repository/factory/agent 추상화를 남발하지 않는다.
- 불확실한 요구사항을 코드에 임의로 확정하지 않는다. 가정이나 TODO에 근거와 담당자를 기록한다.
- 테스트하지 않은 동작을 '완료'라고 보고하지 않는다. Mock·샘플·실데이터를 명확하게 표시한다.
- 설정값(모델명, 임베딩 차원, 컬렉션명, DB 주소, 시간 초과, 청크 크기)은 한 곳에서 관리한다.

### 권장 명명·형식

| 대상 | 규칙 | 예 |
|---|---|---|
| Python 파일·함수·변수 | `snake_case` | `collect_policy_documents()` |
| Python 클래스·Pydantic 모델 | `PascalCase` | `PolicyDocument` |
| 상수·환경변수 | `UPPER_SNAKE_CASE` | `QDRANT_COLLECTION` |
| TS 변수·함수 | `camelCase` | `fetchPolicyDetails()` |
| React 컴포넌트·TS 타입 | `PascalCase` | `PolicyResultCard` |
| JSON/API 필드 | **`snake_case` 권장** | `document_id`, `source_url` |
| Git 브랜치 | `feature/<area>-<task>` | `feature/data-lh-parser` |

기존 저장소에 합의된 형식이 있으면 그것을 따른다. 포맷터(Ruff/Black 또는 Prettier/ESLint 등)는 팀에서 도구·설정을 확정해 통일하고, 개인별 설정 충돌로 대규모 포맷 변경을 만들지 않는다.

## 4. 코드 구조 및 담당 경계

실제 폴더 구조는 저장소 생성 시 확정하며, 아래는 **권장 논리 경계**다.

```text
frontend/                 # 화면·상태·API 호출
backend/
  api/                    # FastAPI 라우터 및 스키마
  services/               # 정책 조회·자격 판단·답변 조합
  rag/                    # 검색 결과 결합·LLM 호출
  graph/                  # Neo4j 연동
  vector/                 # Qdrant 연동
  schemas/                # 팀 공통 입출력 계약
  config/                 # 환경설정
data/                     # 원본·정제 데이터
collectors/               # [위치 합의 필요] 정책 API/PDF 수집
preprocessing/            # [위치 합의 필요] 정제·추출
scripts/                  # 적재·재실행 유틸리티
tests/                    # 단위·통합·평가 테스트
docs/                     # 산출물 01~05 및 계약·운영 절차
```

> 위 트리는 책임을 설명하기 위한 예시이며, `data/`, `tests/`, `collectors/`, `preprocessing/`의 실제 배치는 **PRD 및 팀 합의로 하나만 선택**한다. 프로젝트 내에 동일 기능의 폴더를 중복 생성하지 않는다.

### WBS 역할 기준

| 역할 | 담당 | 주로 관리하는 계약/코드 |
|---|---|---|
| 데이터·API 신청·전처리, 산출물 01·README 취합 | 장반석 | 원본/정제 데이터, 출처 목록, 수집·정제 실행 방법 |
| 임베딩·DB, 산출물 02 | 주민혁 | Neo4j/Qdrant 적재, 스키마·인덱스, 임베딩 설정 |
| 검색·조건 확인·평가, 산출물 05 | 나지인·박소희 | 검색 함수, `backend/eligibility/`에서 입력 검증·정책 조건 비교, 평가 질문·기대 근거·실측 결과 |
| LLM·RAG, 산출물 04 | 나지인·박소희 | 검색 근거·조건 결과를 답변에 연결 |
| React 시연 UI·발표, 산출물 03 | 강민지 | `frontend/`에서 질문·선택 조건 입력, 답변·공식 출처·추가 확인 항목 표시, 실행·시연 정리 |

> 3차 발표는 React 단일 화면으로 시연하고 터미널·노트북은 백업으로 둔다. 정책 조건 비교와 판정은 백엔드에서 수행하며 화면은 반환된 결과를 표시한다.

나지인·박소희의 검색/LLM 내부 분담은 WBS에 별도 확정돼 있지 않다. 같은 파일을 수정할 경우 사전에 협의한다. 공용 스키마·설정·README 변경은 영향받는 담당자에게 PR에서 알린다.

## 5. 데이터 수집 및 전처리 (데이터 담당 핵심)

### 5.1 원본과 출처

- **공식 사이트·허용된 API·공고 원본**을 우선한다. 수집에 앞서 API 승인·호출 제한·서비스 약관·재배포 제한을 확인한다.
- `raw/` 원문은 가능한 한 그대로 보존하고, 정제 결과는 `processed/`로 분리한다. 원문을 덮어쓰지 않는다.
- 모든 문서에 `document_id`, `policy_id`(연결되는 경우), `source_url`, `source_type`, `collected_at`을 기록한다.
- 확인 가능한 경우 `published_at`, `effective_at`, `application_start/end`, 원본 파일 해시, PDF 페이지/문단 위치, 정정공고 이력을 기록한다. **모르는 날짜는 추정하지 않고 `null`/미확인 상태로 둔다.**
- 출처가 없는 텍스트는 실데이터로 적재하지 않는다. 추출 실패·불완전 문서는 상태와 이유를 기록한다.
- 자동 수집이 불가하면 수동 확보 원문 + 동일한 전처리 인터페이스로 대체한다. API 키 승인 지연을 숨기지 않는다.

### 5.2 전처리

- 텍스트 인코딩은 UTF-8을 기본으로 한다. 날짜는 ISO 8601, 시간 기준은 명시적으로 `Asia/Seoul` 등으로 기록한다.
- HTML 메뉴·광고·반복 내비게이션은 제거하되, **자격 예외·각주·표의 행/열 관계·부정문·단위**를 함부로 삭제하지 않는다.
- PDF는 제목·소제목·문단·페이지를 보존한다. 스캔 이미지·표 추출 실패는 임의 보정하지 않는다.
- 원문에 없는 자격 조건을 LLM 추측으로 채우지 않는다. 자동 추출 필드는 원문 근거와 검수 상태를 동반한다.
- 원본 건수 → 제거·중복 건수 → 최종 건수를 기록하고, 변환 실패 샘플을 남긴다.
- 재수집·재실행 시 중복 정책/문서를 무제한 추가하지 않도록 안정적 ID와 콘텐츠 해시를 사용한다.

### 5.3 함수 예시

```python
from datetime import datetime, timezone


def normalize_document(raw: dict) -> dict:
    """필수 식별자와 출처를 검증한 뒤 공통 형식으로 변환한다."""
    document_id = raw.get("document_id")
    source_url = raw.get("source_url")
    content = (raw.get("content") or "").strip()

    if not document_id or not source_url or not content:
        raise ValueError("document_id, source_url, content는 필수입니다")

    return {
        "document_id": document_id,
        "policy_id": raw.get("policy_id"),
        "source_url": source_url,
        "content": content,
        "collected_at": datetime.now(timezone.utc).isoformat(),
    }
```

실서비스에서는 URL 형식, 필드 타입, 날짜 유효성 등을 Pydantic 또는 합의한 스키마로 추가 검증한다. 위 예시는 함수 구조 설명용이다.

## 6. Graph DB (Neo4j) 규칙

- 노드·관계는 실제 정책 구조를 반영한다. 권장 노드: `Policy`, `Organization`, `Region`, `TargetGroup`, `Requirement`, `SourceDocument` (필요할 때 `DocumentType`).
- 관계명은 `UPPER_SNAKE_CASE`로 통일한다: `ADMINISTERED_BY`, `TARGETS`, `HAS_REQUIREMENT`, `SUPPORTED_BY` 등.
- `policy_id`, `document_id`, `requirement_id`는 **의미가 변하지 않는 안정적 식별자**로 관리한다. 이름·제목 자체를 유일키로 사용하지 않는다.
- `MERGE`와 유니크 제약/인덱스를 활용해 재적재 중복을 방지한다. 삭제·전체 초기화는 명시적 개발 환경에 한정한다.
- 정책 조건의 `AND`/`OR`, 예외·제외·기준일을 단순한 노드 연결로 오해하지 않는다. 필요한 규칙 그룹을 명시한다.
- **Graph DB의 관계 탐색 ≠ 법적 자격 확정.** 실제 조건 비교는 검증된 Python 로직과 원문 근거를 함께 사용한다.
- 사용자 입력을 문자열로 Cypher에 이어 붙이지 않는다. **파라미터화된 쿼리**를 사용한다.
- Graph 결과는 최소한 `policy_id`, 관계/조건 식별자, 근거 `document_id`를 반환할 수 있도록 한다.

## 7. Vector DB (Qdrant) 및 임베딩 규칙

- 청크에는 `chunk_id`, `document_id`, `policy_id`(해당 시), `content`, `source_url`, `page_number`/`section_title` 등 출처 추적 필드를 보존한다.
- 청크 분리는 제목·항목·표·예외조건을 고려한다. 임의 고정 길이만 고집하지 않고 평가 질문으로 품질을 확인한다.
- 임베딩 모델명·버전·차원·전처리 방식·청크 크기·오버랩·컬렉션명을 기록한다. **모델 변경 시 차원/인덱스 호환을 검증**한다.
- 검색 점수는 해당 모델/설정에서의 상대 신호이며, 이를 그대로 '자격 적합도'라고 표시하지 않는다.
- 검색 결과는 본문과 함께 `chunk_id`, `document_id`, `policy_id`, `source_url`, 위치 정보를 전달한다.
- 원문 수정/정정 시 오래된 청크와 신규 청크가 섞이지 않도록 버전·재적재 정책을 기록한다.
- 임베딩 API로 원문·개인정보를 전송할 때 외부 제공 가능 여부를 확인한다. 샘플 프로필은 가상 정보 사용을 원칙으로 한다.

## 8. Graph + Vector 공통 데이터 계약

**공통 계약은 DB 구현보다 먼저 합의한다.** 두 DB 간 연결은 `policy_id`, `document_id`를 기본으로 하고, `chunk_id`는 Vector 검색 결과 내 위치 추적에 사용한다.

### 정제 문서 예시 (가상 데이터)

```json
{
  "document_id": "DOC_SAMPLE_001",
  "policy_id": "POL_SAMPLE_001",
  "title": "예시 청년 지원사업 공고",
  "source_type": "pdf",
  "source_url": "https://example.org/sample.pdf",
  "collected_at": "2026-11-04T00:00:00+09:00",
  "published_at": null,
  "content": "실제 수집·검증한 문서 원문 텍스트를 넣습니다.",
  "verification_status": "sample_only"
}
```

> `example.org`와 본문은 **형식 설명을 위한 가상 값**이며 실제 정책 출처로 사용하지 않는다.

### 검색·답변 사이 최소 계약(제안)

```json
{
  "query": "신혼부부 매입임대 신청 서류가 궁금해요",
  "retrieved_chunks": [
    {
      "chunk_id": "CHUNK_SAMPLE_001",
      "document_id": "DOC_SAMPLE_001",
      "policy_id": "POL_SAMPLE_001",
      "content": "근거 문단 예시",
      "source_url": "https://example.org/sample.pdf",
      "page_number": 3,
      "score": 0.72
    }
  ],
  "eligibility_status": "needs_more_info"
}
```

`score`는 예시 수치이며 실제 검색 성능을 의미하지 않는다. 필드명과 필수/선택 여부는 DB·검색·RAG·조건 확인 담당이 **11월 6일 개발 전에** 합의한다. 변경 시 스키마 버전 또는 변경 이력을 남긴다.

## 9. Python / FastAPI

- Python은 타입 힌트와 간결한 `snake_case` 명칭을 사용한다.
- FastAPI 라우터는 HTTP 경계·입력 검증·상태 코드, 서비스 함수는 실제 조회/판정/조합을 담당한다.
- 공개 API의 JSON과 DB 타입은 Pydantic 모델 등으로 **런타임 검증**한다.
- 네트워크/모델/DB 호출에는 타임아웃과 예측 가능한 예외 처리를 둔다. `except Exception: pass`로 실패를 숨기지 않는다.
- 반복 API 호출에는 공식 제공량을 지키는 속도 제한·재시도(backoff)를 적용한다. 무한 재시도 금지.
- 비밀키·개인 프로필·원문에 포함된 민감정보는 로그로 출력하지 않는다.
- 로깅은 `logging` 등 구조화 가능한 방식으로 하며, 작업 ID·문서 ID·실패 단계 등 **민감하지 않은 진단 정보**를 기록한다.

## 10. RAG / LLM / LangChain·LangGraph

- RAG의 목표는 **원문 근거를 찾고 그 범위에서 답하기**다. 답변의 지원 금액·기간·자격 조건을 근거 없이 만들어내지 않는다.
- 프롬프트에는 사용자 질문, 최소한의 허용된 프로필 정보, 검색된 본문과 출처 ID만 필요한 범위에서 전달한다.
- **검색 문서와 웹페이지 안의 지시문을 시스템 명령으로 취급하지 않는다.** 외부 문서는 불신 데이터다.
- 정책과 사용자의 관계가 불명확하면 `추가 확인 필요`를 반환하고 무엇이 부족한지 질문한다. 원문에 정보가 없으면 `근거 없음`을 명시한다.
- `조건상 적합`, `추가 확인 필요`, `조건 불일치`, `접수 대기/마감` 등 상태를 구분하되, 모든 상태를 실제 법적 수급 확정으로 표현하지 않는다.
- 프롬프트 템플릿·모델명·temperature·검색 top_k·청크 전략의 실험값을 기록한다.
- LangGraph 노드는 이름과 입력/출력 상태를 명확히 하며, 단순 조건 비교/DB 호출에 불필요한 LLM Agent를 만들지 않는다.
- LLM 호출 성공과 **답변의 근거 일치**는 별도 검증한다.
- 실제 비용/토큰/지연시간은 가능한 범위에서 측정하되 개인정보를 기록하지 않는다.

## 11. TypeScript / React / UI

> **웹 UI는 React 사용 확정.** 3차는 최소 시연 화면을 준비하며 정식 웹 UI 개발은 4차 범위다. 아래는 **React·TypeScript 사용 시** 적용한다. Next.js 전용 `app/` 규칙을 강제하지 않는다.

- 페이지는 화면 구성, 컴포넌트는 표현, API 클라이언트는 서버 통신을 담당하도록 나눈다.
- 화면 표시는 API 계약을 기준으로 하며, `any` 대신 명시적인 타입을 사용한다.
- 사용자 입력 유효성 검사는 프론트와 서버 양쪽에서 수행한다.
- **정상 답변 / 조건 확인 필요 / 근거 없음 / 로딩 / API 오류**를 각각 다른 상태로 표현한다.
- 정책 카드에 근거 출처, 원문 링크, 기준일 또는 확인 시점을 표시할 수 있도록 데이터를 유지한다.
- UI의 `신청 가능` 문구가 최종 판정이나 접수 중임을 암시하지 않도록 주의한다.
- 공통 버튼·카드·출처 표기 컴포넌트를 재사용하되, 시안에 없는 컴포넌트를 무조건 미리 만들지 않는다.
- 반응형에서 정책 제목·서류 목록·긴 URL·출처 정보를 잘리지 않게 처리한다.
- 디자인 시안 또는 브레이크포인트가 합의되지 않았다면 임의의 LabBridge 디자인/컴포넌트명을 사용하지 않는다.

### 예시 (React/TS)

```tsx
interface PolicySummary {
  policy_id: string;
  title: string;
  source_url: string;
}

function PolicyList({ policies }: { policies: PolicySummary[] }) {
  if (policies.length === 0) {
    return <p>확인된 정책이 없습니다.</p>;
  }

  return (
    <ul>
      {policies.map((policy) => (
        <li key={policy.policy_id}>
          <a href={policy.source_url} target="_blank" rel="noopener noreferrer">
            {policy.title}
          </a>
        </li>
      ))}
    </ul>
  );
}
```

## 12. 보안·개인정보·데이터 품질 필수 수칙

- `.env` 실파일, API 키, 인증 토큰, 계정 정보는 커밋하지 않는다. `.env.example`에는 **변수명만** 공유한다.
- 실제 주민등록번호·신분증·소득증빙·가족관계 서류는 MVP 시연 데이터에 사용하지 않는다. 테스트 프로필은 가상으로 만든다.
- 프롬프트와 RAG 검색 로그에도 사용자의 실명·민감한 가구 정보가 남지 않도록 최소화/마스킹한다.
- 로그인·프로필 저장 기능을 실제 추가한다면 서버 측 인증/인가, 개인정보 보관·삭제 정책을 선행 합의한다.
- 정책 원문은 공신력 있는 출처와 수집 시점을 함께 보여준다. 정정공고·마감/폐지 등 상태 변화에 유의한다.
- 공개 출처 텍스트나 API 응답은 XSS/프롬프트 인젝션이 가능한 외부 데이터로 취급한다.
- DB 초기화·스키마 변경은 재생성 명령·백업·영향 범위를 기록하고 팀과 합의한다.

## 13. 테스트와 재현성

테스트 우선순위는 **문서 근거가 틀리거나 개인정보가 노출되는 위험**을 기준으로 정한다.

| 담당 경계 | 최소 검증 |
|---|---|
| 수집·전처리 | 원문 접근, 출처 URL, ID 누락, 인코딩, 중복, 전후 건수, PDF 페이지 보존 |
| Graph DB | 노드·관계 건수, 정책-조건 연결, 재적재 시 중복, 원문 문서 ID 조회 |
| Vector DB | 청크 수, 임베딩 차원, 검색 결과의 출처/페이지, 재적재 검증 |
| 검색·평가 | 공통 질문 10개, 근거 문서 적중, 부정확한 검색/근거 부재 사례 기록 |
| LLM·RAG | 근거 기반 답변, 추가 질문, 근거 없음, 잘못된 인용, 모델 오류 |
| 조건 확인 | 입력값 검증, 연령·지역 경계값, 신청기간 마감/대기 구분, 입력 누락 시 미확인·부족 항목 반환 |
| UI (4차) | 질문→답변→출처, 로딩/빈 결과/오류, 기본 모바일 표시 |

- 최소 1개 이상의 **가상 정책 샘플**로 스키마 단위 테스트를 작성하고, 별도로 **실제 원문** 기반 통합 테스트를 수행한다.
- 실행 명령과 환경변수, 필요한 DB 시작 방법, 데이터 적재 순서, 테스트 실행 방법을 README에 기록한다.
- 성공 사례뿐 아니라 실패 사례와 제한 사항을 산출물 01·05에 남긴다.
- 한 담당자의 코드 변경으로 다른 담당자의 입출력 계약이 바뀌면 작은 연동 테스트를 다시 수행한다.

## 14. Git / PR / 문서 변경

- 작업 전 최신 브랜치·README·PRD·공통 데이터 계약을 확인한다.
- `feature/...` 브랜치에서 작업하고 PR로 합친다. 현재 저장소의 통합 브랜치는 `main`(기본 브랜치)이며, PR 대상도 `main`으로 맞춘다. 작업 브랜치는 최신 `main`에서 만든다.
- PR에는 **무엇을 / 왜 / 어떻게 테스트했는지 / 영향을 받는 API·스키마·문서**를 적는다.
- 다른 담당자의 코드·공통 필드를 수정하면 관련 담당자에게 리뷰를 요청한다.
- 데이터 원본을 대량 커밋하기 전에 크기·라이선스·저장 위치·Git LFS 필요 여부를 확인한다.
- `docs/`의 계약 문서를 바꿨으면 해당 코드/예시 JSON도 함께 확인한다.
- WBS에 따라 데이터 출처·전처리·아키텍처·연동·테스트 결과는 **구현하면서 동시에 문서화**한다.

## 15. GPT / Codex용 작업 지시

AI 코딩 도구에는 다음 순서를 요구한다.

1. 저장소의 `AGENTS.md`(존재 시), PRD, 이 코딩 스타일, API/데이터 스키마 및 관련 기존 코드를 먼저 확인한다.
2. 담당 범위와 팀 간 영향, 필요한 파일을 짧게 정리한다.
3. 기존 구조·계약을 재사용하고 필요한 부분만 수정한다.
4. 정책 사실을 임의 생성하지 않고 원문·버전·출처를 보존한다.
5. 비밀키·민감정보 보호, 입력 검증, 예외 처리를 포함한다.
6. 가능한 린트·타입 검사·단위/통합 테스트를 실행한다.
7. 변경 파일, 실행 방법, 테스트 결과, 남은 미검증 사항을 보고한다.
8. 팀 합의가 필요한 아키텍처/계약 변경은 구현 전에 표시한다.

### Codex용 짧은 지시문

```text
이 저장소의 AGENTS.md(있다면), SSOK PRD, CODING_STYLE.md, 공통 데이터/API 계약을 먼저 확인하세요.
코드는 입력→검증→처리→결과 흐름으로 읽히게 작성하고 과도한 추상화를 피하세요.
Neo4j/Qdrant 간 policy_id·document_id를 유지하고 정책 원문의 출처·기준일·페이지를 보존하세요.
RAG 응답은 검색한 근거를 벗어나 정책 조건을 지어내지 않으며, 정보 부족과 근거 없음을 구분하세요.
API 키·개인정보를 노출하지 말고 변경 후 테스트 결과, 변경 파일, 미검증 사항을 요약하세요.
담당자 공통 스키마나 인터페이스 변경은 임의 확정하지 말고 먼저 알리세요.
```

## 16. PR 리뷰 체크리스트

- [ ] 코드 입력 → 처리 → 출력/오류 흐름이 명확한가?
- [ ] PRD에 없는 기능이나 불필요한 추상화가 추가되지 않았는가?
- [ ] `policy_id`, `document_id`, `chunk_id` 등 식별자 계약을 준수하는가?
- [ ] 정책 사실·자격 조건·기준일·출처를 원문에서 검증했는가?
- [ ] Graph 관계 및 Vector 검색 결과가 동일한 원문으로 추적되는가?
- [ ] 원문 수정/재적재·중복·결측·예외 케이스를 처리했는가?
- [ ] 근거 없음/추가 정보 필요/접수 마감 상태를 혼동하지 않는가?
- [ ] API 키·민감정보가 코드·로그·Git에 노출되지 않는가?
- [ ] 담당자가 변경 이유와 핵심 데이터 흐름을 설명할 수 있는가?
- [ ] 테스트 실행·실패·미검증 사항이 PR에 기록됐는가?
- [ ] 팀 간 계약 변경을 관련 담당자에게 공유했는가?
