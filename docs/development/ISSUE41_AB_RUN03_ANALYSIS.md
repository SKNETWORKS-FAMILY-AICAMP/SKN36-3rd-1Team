# Issue #41 — Qwen3 Embedding 0.6B / 4B 예비 A/B 결과 및 PR 범위

## 실험 목적과 가설

동일한 v1.4.0 B2 청크와 질문에서 4B가 0.6B보다 정확한 답변 근거를 Top-5에
잘 포함하는지 비교한다. 정답 최종 사람 검수 전 예비 결과이며 서비스 기본 모델은
0.6B로 유지한다. 4B는 품질 우선 환경의 추가 검증 후보로 둔다.

주 분석 원본: [run03 summary](experiments/issue41_ab_run03/summary.json).
SHA-256: `619770416363ebfb171d31e4d68de7115b3a08977db95850308305ab7b69a122`.
원본 결과·질문·정답·승인 데이터는 변경하지 않았다.

## 개발 내역

- `A_B2_4B_V140`: 기존 B2 청킹·입력·UUID·payload 계약을 재사용하는 별도 4B 구성.
- `retrieval_v140_eval --mode model-ab`: 모델별 무지시문 질의 임베딩, 동일 질문/Top-5/
  필터/채점, 모델별 timeout, 임베딩·검색 시간 분리.
- `ab_eval_state`: 질문별 원자적 저장·checksum, 중단/timeout 기록, 성공분 재사용,
  모델·컬렉션·질문·코드·환경 identity 불일치 시 재개 차단.
- `embedding_resume`: A/B 주소·컨테이너·볼륨 보호, 기존 Point 불변 검사와 누락분 재개.
- `runpod_transfer`, `scripts/runpod_embed.py`: 고정 841개 입력 export, GPU 벡터 생성
  재개, 기본 읽기 전용 import, 기존 297개 보존, 전수 사후 검증.
- float32 비교 수정: REST 소수 표현을 재정규화 없이 동일 float32 바이트로 비교한다.
  payload 값·타입은 엄격히 유지하며 오차 허용으로 검증을 느슨하게 하지 않는다.

## 평가지표 정의 및 독립 검산

Recall@5는 모든 필수 근거 구간을 Top-5 청크가 완전히 포함한 질문 비율이다.
MRR@5는 마지막 필수 근거가 확보되는 순위의 역수 평균이다. 두 지표의 분모는 52다.
`split_only`, `partial`, `doc_only`는 완전 성공이 아니다. 일반적인 정책 단위
Recall/MRR과 구분하며, `verified_exact`는 최종 사람 정답 검수를 의미하지 않는다.

채점 함수를 재호출하지 않고 문서 ID와 문자 구간 포함 관계로 성공·순위를
독립 재계산했다. 모델별 55개 고유 질문·채점 52개·누락/중복 0개를 확인했다.
110개 질문 저장 파일의 identity·row checksum과 summary의 일치도 확인했다.

부합하지만 로딩만 분리한 시간은 없다. 첫 질문 제외 참고 합산 평균은 907.00ms /
963.04ms다. 참고값으로만 사용하고 정식 집계를 교체하지 않는다.

### run02도 보존하는 이유

[run02 summary](experiments/issue41_ab_run02/summary.json)도 PASS이며 run03과 평가
identity가 같고 Recall/MRR도 같다. 합산 평균은 run02에서 1593.41 / 1001.37ms,
run03에서 954.46 / 997.75ms였다. 시간 변동을 숨기지 않도록 두 실행의 핵심 원본을
함께 PR 후보로 둔다. run03은 요청된 주 분석 실행이지 시간상 유리한 값만 선택한
일반 성능 결론이 아니다. 반복·순서 교차 측정 전 속도 우위를 확정하지 않는다.
특히 run02의 0.6B RQ001은 29.432초로 run03의 3.509초보다 길었다.
최초 요청 지연 차이는 확인되지만 로딩만 분리한 값이 없어 그 원인을 단정하지 않는다.

## 결과 해석과 모델 선택 권고

0.6B 기준선을 유지하고 4B는 품질 우선 GPU 환경의 추가 검증 후보로 둔다.
4B의 Recall 이득은 실측됐지만 차이가 난 질문은 5개뿐이며 Top-1 수는 줄었다.
개선 4 / 악화 1에 대한 참고 paired exact 검정은 p=0.375로 확정적 우위를 주장하지 않는다.

모델 파일은 약 0.64 / 2.50GB, 실행 시 관측된 모델별 VRAM은 약 4.32 / 7.25GiB였다.
두 모델이 함께 적재된 기록도 있다. 원시 벡터 저장량은 약 4.45 / 11.11MiB로
4B가 2.5배다. 관측 VRAM은 최소 요구량이 아니며 과금 자료가 없어 금액 비용을
산정하지 않는다. 이 속도를 노트북 CPU나 로컬 GPU 성능으로 환산하지 않는다.

## 한계 및 후속 개선 계획

1. 정답은 최종 사람 검수 전이다. RQ017·RQ018은 대체 근거/질문 범위 검토 대상으로만 둔다.
2. 0.6B Q8_0와 4B Q4_K_M은 양자화가 달라 순수 파라미터 수만의 비교가 아니다.
3. 4B 색인은 CPU 297개 + RunPod GPU 841개다. 동일 digest·입력이어도 하드웨어,
   backend·Ollama 버전에 따른 수치 차이 가능성을 제거한 실험은 아니다.
4. SSH 왕복, 로딩 상태, 고정 모델 순서·캐시·동시 적재가 시간에 영향을 준다.
5. 다음 평가는 골드 검수, 다양한 실사용형 질문, 모델 순서 교차·반복 실행으로 보완한다.
6. RQ020 같은 근거 누락에는 Hybrid/reranker/섹션 검색을 별도 실험한다.
7. 최종 승인 데이터가 바뀌면 입력·metadata·ID·manifest를 다시 검증한다. 이번 작업에서는
   재평가나 DB 재적재를 하지 않았다.

`.env`, 모델·DB 볼륨·snapshot·백업. 승인 데이터·freeze·정답 및 #43 파일은 수정/포함하지 않는다.
새 ignore 규칙 대신 명시적 파일 목록으로 PR 범위를 제한한다. 아직 staging/commit은 하지 않는다.
